## 0. 已确认的决策

| 编号 | 决策 |
|---|---|
| Q1 | **混合 LAN 判定**：默认按「出口 IP + 客户端上报的私网 /24」近似分组并标注「推测同网」；用户可绑定「网络标识」获得精确分组。跨网房间不出现在列表，只能凭房间号加入 |
| Q2 | **Go 单二进制服务端 + 原生 ES Modules 前端**，零数据库、零前端框架、零构建步骤。服务端**零第三方依赖**（标准库手写 RFC6455 WebSocket），可离线 `go build` |
| Q3 | **允许多进程/多端口** → 自建 `coturn` 改为**可选**（compose profile）。**`LANSHARE_STUN_URLS` 与 `LANSHARE_TURN_URLS` 都未配置时**（默认）服务端下发 `ice.noIceServers=true`，跨网直接由 LANShare 自身经 WS `relay` + `relay_data` **完整中继聊天与文件**（复用 443、零新增端口与依赖、仅内存转发不落盘）；配置了任一则正常走 ICE，只有明确失败才落 WS 兜底 |
| Q4 | 历史只同步文本与文件「卡片元数据」；历史上限 **200 条 / 2MB**，仅内存，刷新页面清空，服务端不落盘 |
| Q5 | 历史文件本体不做房间级缓存，卡片标记「仅当在线设备仍持有该文件时可接收」，仍可点「接收」向全房在线成员重新取片 |
| Q6 | 单文件上限 **2GB**（所有设备一致），chunk **128KB**（原设计 256KB 恰等于部分浏览器 DataChannel 单消息上限，留余量后下调）；移动端默认**仅 WiFi 供种**；支持进度 / 暂停 / 取消 / 清理缓存后重新下载 |
| Q7 | 房间号 **6 位 Crockford Base32 短码**；全员离线即销毁；创建者为房主，可踢人/解散，房主离线自动移交给最早在线成员；密码连错 5 次锁定 30s |
| Q8 | 所有房间用房主生成的随机会话密钥做 **AES-256-GCM** 应用层加密（文本、元数据、文件 chunk 全量）；私有房密码仅用于准入并包装该密钥；全局限流 |
| Q9 | 每房 **10 人**；下载最多同时从 **4 个源**取分片；优先同 LAN 源，外网源补位 |
| Q10 | 私有房在列表中显示名称 + 锁图标，点进去才要密码 |

补充决策（未在 Q 列表中、按推荐默认执行）：

- **必须 HTTPS**：WebRTC 要求安全上下文。生产用域名 + 正式证书；局域网可用自签证书（手机需手动信任）；`localhost` 可走 HTTP 仅用于开发。
- 静态资源由 `go:embed` 打进二进制，单端口提供页面 + 信令；**默认不部署 coturn**，只有需要标准 TURN 时才以可选 compose profile 启动独立进程（3478 UDP/TCP + 中继端口段）。无外部 STUN/TURN 时由本进程的 WS 内存中继兜底。

## 1. 需求与验收标准

| # | 需求 | 验收方式 |
|---|---|---|
| 1 | 浏览器打开即用、响应式 | 手机/电脑浏览器直接访问，无安装、无插件；窄屏单列、宽屏双列，按钮触控 ≥44px |
| 2 | 占用小、效率高、易维护 | 服务端单二进制、内存态、零 DB；`go build` 无外部依赖；前端无打包 |
| 3 | 自动列出同 LAN 房间 | 同 WiFi 两台设备打开首页，互相看到房间卡片；跨网设备看不到 |
| 4 | 公开 / 私有房 | 公开房直接进；私有房密码错误进不去，正确可进 |
| 5 | 跨网按房间号 / 分享链接加入 | 手机切 4G 输入房间号，或扫房间页「分享链接」二维码，可加入电脑创建的房间 |
| 6 | 内网直连 / 外网打洞 / 转发兜底 | 同 LAN 走 host candidate（不经服务器传业务数据）；配了 STUN/TURN 时跨网 srflx 成功则直连、失败走 TURN；**默认未配置任何外部 ICE 服务器时跨网直接由服务器 WS 完整中继，聊天与文件均可用** |
| 7 | 房间广播 + 历史同步 | 后加入者能看到加入前的文本；服务端进程内 grep 不到任何聊天内容字段 |
| 8 | 文本 + 文件，主动点接收 | 文件卡片出现时不产生文件流量；点「接收」才开始传 |
| 9 | 多源 P2P 下载 | A 发文件，B 下完后 C 下载时同时从 A、B 取不同分片；B 下线后 C 仍可从 A 下完 |

## 2. 总体架构

```
  ┌─────────────────────── 浏览器 A/B/C ───────────────────────┐
  │  UI(响应式)  Room(状态/历史)  RTC(网格)  File(分片调度)  Crypto │
  │                     ↕ WebSocket(JSON 信令)                  │
  └──────────────────────────┬──────────────────────────────────┘
                             │ WS: hello/list/create/join/signal/relay/relay_data/relay_pause/...
                    ┌────────▼─────────┐
                    │  Go 单二进制服务  │  embed 静态页 + 信令 + 房间表(内存)
                    │  :8080 (HTTP)    │  不存历史、不存文件、不存聊天内容
                    └────────┬─────────┘
                             │ 下发 ICE 配置与临时凭据
          ┌──────────────────┼───────────────────────┐
          ▼                  ▼                       ▼
   STUN(配了才打洞)  coturn(:3478, 可选)  WS 完整中继(默认/兜底)
                                          (聊天 + 文件，仅内存转发)
  ┌──────────────────────────────────────────────────────────┐
  │ host(内网直连) > srflx(打洞) > relay(TURN) > WS relay       │
  │ P2P 走 DataChannel；WS relay 复用同一条 443 连接           │
  └──────────────────────────────────────────────────────────┘
```

**三条铁律**

1. 配置了 STUN/TURN 时服务端**只转发信令**，业务帧（`chat`/`file_offer`/`file_have`/`file_want`/chunk）绝不经过服务端；**默认未配置任何外部 ICE 服务器时**（以及 ICE 明确失败时）由 WS 中继在内存透传，服务端**不解析、不落盘、不缓存**。
2. 服务端**不持久化任何东西**：房间表、成员表、密码哈希、限流计数全在内存，进程重启即清空。
3. 历史**只存在于在线客户端内存**，由客户端之间 P2P 补发。

## 3. 技术选型与理由

| 层 | 选择 | 理由 |
|---|---|---|
| 服务端语言 | Go 1.27 标准库 | 单二进制、`go build` 离线可过、内存约 10~20MB、并发模型天然适合长连接 |
| WebSocket | 标准库手写 RFC6455 | 避免 `gorilla/websocket` 等外部依赖与 `go.sum` 网络拉取；约 150 行可控代码 |
| 静态资源 | `embed.FS` | 部署只有一个可执行文件 |
| 前端 | 原生 ES Modules + HTML/CSS | 无 npm、无构建、改完刷新即生效；ESM 天然模块化 |
| 传输 | WebRTC `RTCDataChannel` | 浏览器唯一能主动 P2P 互联并跑满内网带宽的方式；DTLS 自带加密 |
| 打洞/兜底 | 可选 STUN/TURN + 服务器 WS 完整中继 | **默认不配置任何外部 ICE**，跨网直接由服务端经 WS 内存中继聊天与文件（只走 443、不落盘）；需要打洞才配 STUN，需要标准 TURN 才启用可选 coturn profile，临时凭据由服务端签发 |
| 文件缓存 | IndexedDB 按 chunk 存储 | 避免 2GB 文件占满 JS 堆；支持随机读供种、刷新后可清理 |

## 5. 协议规范

### 5.1 客户端 ↔ 服务端（WebSocket 文本帧，JSON）

公共字段：`t` = 类型。服务端下发统一带 `from`（服务端签名时填写）或显式 `ok`/`err`。

| 方向 | `t` | 主要字段 | 说明 |
|---|---|---|---|
| C→S | `hello` | `v,nick,netId?,lan?` | 建立会话；`nick` 为空时由服务端分配随机昵称 |
| S→C | `welcome` | `peerId,nick,ice,scope,limits` | `nick` 为服务端最终昵称；`ice={iceServers:[...], noIceServers:bool}`，后者为 true 表示未配置任何外部 STUN/TURN，前端直接走 WS 中继 |
| C→S | `list` | — | 拉取同 scope 房间列表（前端 5s 轮询） |
| S→C | `roomlist` | `rooms:[{rid,name,private,members,approx}]` | 只返回同 scope |
| C→S | `create` | `name,password?,keySalt,encKey?,netId?,lan?` | 随机房间号创建；`encKey` 是密码包装后的会话密钥密文 |
| C→S | `enter` | `rid,name?,password?,keySalt,encKey?,netId?,lan?` | **单一入口**：房间存在则走 `joinVerify` 加入；不存在则按该 `rid` 创建并回 `created`。`rid` 必须是 6 位 Crockford Base32 |
| S→C | `created` | `rid,host,salt,private,name` | `salt` = 包装盐 `keySalt` |
| C→S | `join` | `rid,password?,netId?,lan?` | 加入房间 |
| S→C | `joined` | `rid,name,private,host,nick,salt,encKey,peers[],syncFrom,ice` | `nick` 已保证房间内唯一；`encKey` 为空时向 `syncFrom` 索取会话密钥 |
| S→C | `peer_join` / `peer_leave` / `host_changed` | `peer{id,nick,sameLan}` / `id` | 成员变更广播 |
| C→S | `set_password` | `password,keySalt,encKey?` | **房主**：添加 / 修改 / 移除密码；`password=""` 即移除 |
| S→C | `room_meta` | `private,salt` | 广播给全房；只更新 UI，不改变任何成员的会话密钥 |
| C→S | `set_nick` | `nick` | 随时改名；服务端保证房间内唯一 |
| S→C | `peer_nick` / `nick_set` | `id,nick` / `nick` | 成员昵称广播 / 改名回执 |
| C→S | `signal` | `to,data` | `data` 为 `{sdp}` 或 `{candidate}`，服务端补 `from` 后转发 |
| S→C | `signal` | `from,data` | — |
| C→S | `bindnet` | `netId` | 绑定/切换网络标识，重算 scope |
| S→C | `scope` | `key,kind,label` | `kind = net \| approx` |
| C→S | `leave` / `kick` / `close_room` | `id?` | `kick`/`close_room` 仅房主可用，服务端校验 `HostID` |
| C→S | `relay` | `to,bin` | **兜底控制帧**：base64 业务 JSON，仅内存转发，不落盘 |
| S→C | `relay` | `from,bin` | — |
| C→S | `relay_data` | `to,k,bin` | **兜底数据帧**：`k=data\|direct`，`bin` 为已打包/已加密整帧的 base64 |
| S→C | `relay_data` | `from,k,bin` | 服务端原样透传，不解码业务内容 |
| S→C | `relay_pause` | `ms` | 接收端队列拥塞时发给发送方，令其暂停推流 `ms` 毫秒（尽力而为，可丢弃） |
| S→C | `kicked` / `room_closed` | `rid` | 被踢 / 房间解散 |
| S→C | `error` | `code,msg` | `bad_password / room_full / not_found / rate_limited / locked / forbidden / bad_frame` |

> `relay` 限 ≤64KB；`relay_data` 限 base64 文本 ≤256KB（解码后 ≤192KB），`k` 只允许 `data` / `direct`。两类帧共用 1000 帧/s 的次数限制；`relay_data` 默认**不限速**（`relayDataLimit=nil`），需要限流时用 `LANSHARE_RELAY_RATE_MB` / `-relay-rate` 设每连接 MB/s 上限。服务端只做房间成员校验与透传，不落盘；拥塞时 `relayEnqueue` 先短等排空，仍放不下才丢帧并回 `relay_pause`，**不会像普通 `sendJSON` 那样直接关闭接收端连接**，缺片由文件层重传补齐。

### 5.2 客户端 ↔ 客户端（DataChannel）

每个 `RTCPeerConnection` 建立三类通道（同一时刻只有一种数据模式活跃）：

| 通道 | 属性 | 载荷 |
|---|---|---|
| `ctrl` | 可靠、有序 | JSON 文本（见下表） |
| `data0`…`data2` | 可靠、有序 | P2P 分片模式的二进制 chunk；3 条通道均衡缓冲（`max-bundle` 下共享同一 SCTP 拥塞窗口，不叠加带宽） |
| `direct` | 可靠、**无序** | 两人直传模式的连续字节流帧；无序可靠避免单个丢包阻塞整条流。每次直传建立 `DIRECT_PCS`（默认 3）条独立 RTCPeerConnection，每条关联 1 条 `direct` 通道——**独立 SCTP 关联 = 独立拥塞窗口**，可成倍放大吞吐；发送端按各通道缓冲最空的那条推，接收端仍按绝对 offset 重组 |

`ctrl` 帧：

| `t` | 字段 | 说明 |
|---|---|---|
| `chat` | `id,ts,from,nick,text` | 文本消息，全房广播 |
| `file_offer` | `id,ts,from,nick,file{fid,name,size,mime,chunkSize,count}` | 文件卡片，**不含数据、不含逐片校验表**（元数据极小） |
| `file_have` | `fid,bits(base64 bitset)` | 供种位图，增量广播（每 64 片 = 8MB 或完成时） |
| `file_want` | `fid,gen,want,mod,total` | **单次订阅**（P2P 模式）：接收端把缺失位图与取模分工发给源，源据此单向持续推流；`gen` 让上一代 pump 退出 |
| `file_got` | `fid,gen,bits` | 每 3s 同步已收位图，让源跳过重复片 |
| `direct_want` | `fid,gen,offset,block` | **单次订阅**（两人直传）：从 `offset` 起把文件当连续流推完；`block` 是本端按 SCTP `maxMessageSize` 协商出的帧大小 |
| `direct_stop` | `fid` | 停止直传泵 |
| `file_stop` | `fid` | 停止推送（暂停 / 取消 / 完成 / 重新分工） |
| `file_req` | `fid,i,n?` | 仅为兼容旧版本保留：旧端发来时回单片 |
| `file_cancel` | `fid` | 取消，供种方停止回片 |
| `file_done` | `fid` | 某 peer 完整下载完成 |
| `key_req` | — | 公开房新成员向 `syncFrom` 索取会话密钥（**明文帧**，仍受 DTLS 保护） |
| `key_sync` | `key(base64 32B)` | 单播回传会话密钥；接收方只接受 `joined.syncFrom` 指定的来源 |
| `sync_req` | — | 新成员向 `syncFrom` 请求历史（密钥就绪后才发） |
| `sync_res` | `sid,part,total,data` | 分片返回历史（≤24KB / 片，共 ≤2MB / 200 条） |
| `peer_meta` | `wifi,lan` | 供种能力声明（移动端流量默认不供种） |

`dataN` 二进制帧格式（小端）：

```
偏移  长度  字段
0     2     magic 0x4C53 ('LS')
2     8     fid  (16 位 hex → 8 bytes)
10    4     idx  (uint32 chunk 序号)
14    4     len  (uint32 明文长度)
18    len   payload（私有房为 AES-GCM 密文，含 16B tag）
```

`direct` 二进制帧格式（小端，帧头同为 18B）：

```
偏移  长度  字段
0     2     magic 0x4452 ('DR')
2     8     fid
10    4     offset (uint32，绝对字节偏移)
14    4     len
18    len   payload（私有房为 AES-GCM 密文）
```

两种帧 magic 不同，`parseChunk` / `parseDirect` 互不混淆。直传帧的 AES-GCM nonce 序号由
`floor(offset / 1024)` 派生（而非分片序号），因此从任意段边界续传都不会重用 nonce。

### 5.3 加密规范（会话密钥模型）

设计目标：房主可随时添加 / 修改 / 移除密码，而**已连接成员的密钥不变、不被踢、不需重新输入密码**。

- 房间创建时房主生成 32B 随机 `roomKey`，全生命周期不变；**所有房间**（公开 / 私有）都用它做应用层 AES-256-GCM 加密。
- 私有房：`KEK = PBKDF2-HMAC-SHA256(password, UTF8(keySalt), 120000)`，`encKey = AES-GCM(KEK, roomKey)`。服务端只保存 `encKey` 密文和准入用的 `PBKDF2(password, pwdSalt)`，**永远得不到 roomKey**。
- 新成员取得密钥：
  - 私有房：密码校验通过 → `joined.encKey` + `joined.salt` → 本地解包。
  - 公开房：`encKey` 为空 → 向 `joined.syncFrom` 发 `key_req`，对方单播 `key_sync` 回传 roomKey；拿到密钥后才请求历史，避免历史密文无法解开。
- 改密码：房主用新密码 + 新 `keySalt` 重新包装**同一把** roomKey 上传；服务端只替换 `encKey` / 准入哈希并广播 `room_meta`。在线成员不需任何动作。
- 文本/元数据：`nonce = 12B random`，帧为 `{t:'enc', nonce:b64, data:b64}`。
- chunk / direct 帧：`nonce = fid前4B || seq(4B, BE) || 0x00000000`，`AAD = fid bytes`。分片模式 `seq = idx`，直传模式 `seq = floor(offset/1024)`；每帧独立加密，nonce 全局不重复。
- chunk 完整性由 **DTLS 认证 + SCTP CRC32c + 可靠有序** 保证，应用层不重复计算逐片哈希；帧头 `fid/idx/len` 只用于定位与防串包。
- `key_req` / `key_sync` 用 `plain:true` 跳过应用层加密（此时接收方还没有密钥），但仍受 DTLS 保护。若已降级到 WS relay 兜底，这两个帧会经过服务端内存（不落盘）——这是极端降级场景的已知取舍。

### 5.4 ID 规则

- `rid`：6 位 Crockford Base32（去掉 I/L/O/U），`crypto/rand` 生成，房间表内去重，重启即失效。
- `peerId`：随机 12 位 hex；`id`（消息）：`peerId:8位hex`；`fid`：16 位 hex。
- `nick`：首次访问由服务端随机生成（形容词 + 名词 + 2 位 hex），写入浏览器 localStorage；加入房间时服务端保证房间内唯一，重名自动追加序号。
- 消息去重：每个客户端维护 `seen Set<id>`，历史合并按 `ts` 排序 + `id` 去重。

## 6. 服务端设计

### 6.1 状态

```go
type Hub struct {
  mu       sync.RWMutex
  rooms    map[string]*Room     // rid -> Room
  clients  map[string]*Client   // peerId -> 连接
}

type Room struct {
  RID, Name, HostID, Salt, ScopeKey string
  Private bool
  PwdSalt, PwdHash []byte           // PBKDF2-SHA256，仅内存
  Fail map[string]*FailRec          // 密码失败计数（按 IP）
  Members map[string]*Member
  Order []string                    // 加入顺序，用于房主移交
}
```

**无历史字段、无文件字段、无任何持久化**。

### 6.2 LAN 分组算法（Q1）

```
exitIP = 信任代理时取 X-Forwarded-For 首项，否则 RemoteAddr 的 IP
lan    = 客户端上报的私网 /24（来自 WebRTC host candidate；拿不到则 "?"）
scopeKey(netId, exitIP, lan):
    netId != ""  -> "net|"    + netId              // 精确
    else         -> "approx|" + exitIP + "|" + lan // 推测（lan 未知时为 "?"）

sameScope(a, b)：同为 approx 且出口 IP 相同，且一方 lan 为 "?"（尚未探测完成）
时按通配处理，避免 LAN 探测延迟导致刚创建的房间从列表里"跳组"消失。
```

- 前端通过临时 `RTCPeerConnection` 收集 host candidate 提取私网 IP；Chrome 常返回 `.local` mDNS 名无法解析 → 回落为 `?`，此时仅按出口 IP 分组，并在 UI 标注「推测同网，建议绑定网络标识」。
- `sameLan(a,b)`：`scopeKey` 相同 && `exitIP` 相同 && （双方 lan 均已知则相等）→ 客户端据此优先选内网供种源。
- 列表只返回 `scopeKey` 相同的房间；跨网房间永不下发。

### 6.3 房间生命周期

```
create → 生成 rid/salt → 加入 Hub → 创建者成为房主
join   → 校验密码/人数/限流 → 广播 peer_join → 返回 peers + syncFrom(=房主)
leave  → 移除成员 → 若房主离开，按 Order 移交最早者 → 广播 host_changed
       → Members 为空则 delete(room)，历史随之消失
```

### 6.4 限流与安全

| 项 | 限制 |
|---|---|
| WS 帧 | 文本 ≤1MB，二进制帧一律拒绝；`relay` ≤64KB、`relay_data` ≤256KB（均以文本帧内 base64 承载）；读超时 60s，25s ping |
| 信令频率 | 每连接令牌桶 100/s，突发 200（`relay_data` 不占此额度） |
| 创建房间 | 每 IP 10/min；房间总数 200；每房成员 10 |
| 密码 | 连错 5 次锁 30s；服务端只存 `salt + PBKDF2(password)` 结果 |
| 昵称/房间名 | 长度 ≤24 / ≤32，HTML 在前端转义后插入 |
| 兜底帧次数 | `relay` + `relay_data` 共用 1000 帧/s、突发 2000，防止小帧洪泛；对 128KB 分片约 128MB/s，不构成吞吐瓶颈 |
| `relay` | ≤64KB，仅内存转发 |
| `relay_data` | `k` 白名单 `data`/`direct`；解码后 ≤192KB；**默认不限速**；仅内存转发 |
| 中继带宽（可选） | `-relay-rate` / `LANSHARE_RELAY_RATE_MB`，单位 MB/s，按单个 WS 连接计；`0` = 不限速，设置后使用「rate / burst=2×rate」令牌桶 |
| `relay_pause` | 接收端队列拥塞时回给发送方的节流通知，满队列时直接丢弃，不影响连接 |
| 房主操作 | `kick`/`close_room` 校验 `from == HostID` |

### 6.5 TURN 临时凭据（Q3）

coturn 开启 `use-auth-secret` + `static-auth-secret=<SECRET>`：

```
username   = "<unix时间戳+TTL>:<peerId>"
credential = base64(HMAC-SHA1(SECRET, username))
```

服务端在 `welcome`/`joined` 下发，凭据 1 小时有效，前端不硬编码任何密钥。

### 6.6 手写 WebSocket 要点

- 升级：校验 `Upgrade/Connection/Sec-WebSocket-Key`，回 `101` + `Sec-WebSocket-Accept = base64(SHA1(key+GUID))`。
- 读：解析 FIN/opcode/mask/扩展长度（126/127），处理 continuation 分片、ping→pong、close→关闭；客户端帧必须 masked。
- 写：统一 `writeMu` 串行，避免并发写乱帧；`SetWriteDeadline`。
- 文本业务均为 JSON；`relay` / `relay_data` 用 base64 字符串承载二进制，避免引入二进制 WS 帧类型。

## 7. 前端设计

### 7.1 状态机

```
boot → WS hello（立即，拿到 peerId 并解锁按钮）
     → detectLAN() 并行完成 → bindnet 刷新 scope
     → 首页(房间列表/创建/加入)
          ├─ create/join → 房间页 → 建网格 → sync_req
          └─ leave → 首页
```

`app.state = { conn, self, room, peers:Map, history:[], seen:Set, transfers:Map, key:CryptoKey|null, enc:bool }`

### 7.2 WebRTC 网格

- 每房 ≤10 人，采用**全网格**；`peerId` 字典序**小的一方**向大的一方发 offer，避免 glare。
- 服务端 `peer_join` 触发：已有成员中 id 较小者对新成员发起 offer；`signal` 帧按 `to` 转发 SDP/ICE。
- `iceServers`：按 `LANSHARE_STUN_URLS` / `LANSHARE_TURN_URLS` 下发；两者都留空时为空数组且 `noIceServers=true`。`iceCandidatePoolSize=2`，`bundlePolicy='max-bundle'`。没有外部 ICE 服务器时仍会收集 `host` candidate，内网直连不受影响。
- 判定真实链路：监听 `onicecandidate` 的 candidate 类型（`host`/`srflx`/`relay`）及 `getStats()` 的 `candidate-pair`；UI 显示每位成员的 `LAN / P2P / TURN / 中继` 标记；优先从 `host` 且 `sameLan` 的 peer 取分片。
- **背压**：分片推流高/低水位 `8MB / 4MB`，两人直传为 `2MB / 1MB`（两组独立常量）；WS 中继另有 `4MB / 1MB`。768KB 窗口太小，网络抖动时会反复进入等待，把连续推流切成脉冲，是上一轮「峰值 9.5MB/s、当前 0.77MB/s」的主要成因之一。泵在高水位用 `waitDrain()` 挂起，由 `onbufferedamountlow`（drain）或 16ms 兜底唤醒后继续连续 `send()`，**既不丢帧也不受定时器节拍约束**。
- **帧快路径**：`pushData()` / `pushDirect()` 直接发送已构造好的帧，不再 `parseChunk` / `sealChunk` / 重复打包。分片固定 128KB；直传按 `pc.sctp.maxMessageSize` 减去帧头与 tag 开销，向下对齐到 16KB，上限 1MB（Chrome 默认 256KB → 240KB）。
- **WS 完整中继（模式由配置决定，不再靠运行时猜测）**：服务端 `ice.noIceServers=true`（STUN/TURN 都未配置）时，只给内网 `host` 直连留 `NO_ICE_CONNECT_TIMEOUT_MS=2.5s` 窗口，超时即置 `wsOnly=true` 并调用 `Mesh.setRelayMode(true)`——没有外部 ICE 服务器时 ICE 常长期停在 `connecting` 而不报 `failed`。内网直连若在窗口内建好 ctrl 通道则不切，之后 P2P 恢复也会自动切回。
- 配置了 STUN/TURN 时**不启用抢跑定时器**，完全交给 ICE 协商；只有所有 PC 进入 `failed`/`disconnected`/`closed` 才落 WS 兜底，避免 TURN 尚未建好就被切到慢链路。`scheduleStall()` 每次进房/加人都会重置 `stalled`，不会把上一位成员的超时状态带过来。
- `Mesh` 在 relay 模式下用 WebSocket 整体替换 DataChannel：`ready()` 按 peer 是否存在判定，`channelFor()` / `directChannelFor()` 返回带 `bufferedAmount` 的伪通道（取 `ws.bufferedAmount`，高水位 4MB / 低水位 1MB），`maxMessageSize()` 收窄到 64KB。因此 `FileMesh` / `DirectStream` 的推流泵、多源分工、背压与断点续传代码**一行都不用改**。
- 控制帧走 `relay`，文件分片与直传整帧走 `relay_data`；接收侧 `relayIngest()` 复用与 DataChannel 相同的 `onBinary()`，私有房 AES-GCM 解密口径一致，服务端只见密文。
- `relayData` 发送前检查原始帧 ≤192KB；分片固定 128KB + 帧头 + 16B tag 在范围内，直传块在 relay 模式收窄到 64KB，避免 base64 后超出服务端 256KB 限制。
- **两级背压**：本地看 `ws.bufferedAmount`（4MB / 1MB 水位，不限速时放宽以免把连续推流切成脉冲）；服务端发现接收端队列拥塞则回 `relay_pause`，`Mesh.pauseRelay()` 在暂停期内让 `sendRelay()` 返回 false，泵经 `waitDrain()` 短等重试。背压只做流控、不限制带宽，既不冲垮服务器也不丢链路。

### 7.3 广播与去重

- 发送：本地 `history.push` → `rtc.broadcastCtrl()` 给所有 `open` 的 ctrl 通道。
- 接收：若 `seen.has(id)` 丢弃；否则记录并向其它 peer 转发（网格内做一次中继，容忍非全连接）。
- `ttl` 字段防环路，最大 2 跳。

### 7.4 历史同步（Q4/Q5）

1. `joined.syncFrom` = 房主；新成员与该 peer 的 ctrl 通道 open 后发 `sync_req`。
2. syncFrom 从内存取 `history.slice(-200)`，按 ≤24KB 拆成 `sync_res{sid,part,total,data}` 逐包回传（加密 + WS 兜底 base64 后仍远小于 64KB 限制）。
3. 新成员合并：`id` 去重 + `ts` 升序；文件卡片一律附加 `expired:true`，并为每张卡片补建 leecher；收到在线 peer 的有效 `file_have` 位图即解除过期标记。
4. **位图与卡片乱序**：`file_have` 若早于历史卡片到达，按 `fid` 暂存进 `pendingBits`（60s 过期），`registerOffer` 时合并，不再静默丢弃。
5. **连接建立即宣告**：`mesh.on('ready')` 时本端主动把持有的全部非空位图单播给新连上的 peer。后加入者不必依赖只发给房主的 `sync_req`，也能找到非房主的供种源（包括下载完成者）。
6. 若 syncFrom 在同步完成前离线，服务端在 `host_changed` 后新成员改向新房主重发 `sync_req`。

## 8. 文件网格算法（第 8、9 条）

### 8.1 数据结构

```
Transfer {
  fid, meta{fid,name,size,mime,chunkSize,count},
  role: 'seeder' | 'leecher',
  mode: 'direct' | 'mesh',            // 房间 <=2 人走直传，>=3 人走 P2P 分片
  bits: Uint8Array(ceil(count/8)),   // mesh 持有位图；direct 仅完成时置全 1
  peerBits: Map<peerId, {bits,ts}>,
  offset, block, resumed,            // direct 的续传位置 / 帧大小 / 是否恢复过
  assign: Map<peerId, {mod,total}>,  // mesh 取模分工，最多 4 源
  stats: {rate,peak,dupes,refills,sources,stalled,restoredBytes,...},
  state: 'idle'|'running'|'paused'|'done'
}
```

IndexedDB v2（`lanshare-v1`，升级只新增 store，旧分片数据保留）：

| 数据 | key / store | 说明 |
|---|---|---|
| P2P 分片 | `chunks`，`fid:%08d` | 128KB/片，补零保证范围查询顺序，支持随机读供种 |
| 直传段 | `chunks`，`fid:s%08d` | 4MB Blob/段；`'s'` 字典序在数字之后，与分片范围互不重叠 |
| 传输进度 | `progress`，`fid` | `mesh`: `{bits,bytesDone,havePieces,state}`；`direct`: `{offset,block,state}` |

- 源端按需 `File.slice()` / `Blob.slice()` / IDB 段读取，**不整文件读入内存**。
- 完成后分批 `getAll` 组装 `Blob` → `<a download>` 保存；`progress` 记录保留，重进房点「再次保存」可重新组装。
- 供种能力：`peerBits` 全 1 = 完整下载者；mesh 模式下每 64 片（8MB）广播一次 `file_have`，实现「边下边传」。

### 8.2 双模式传输（按房间人数自动切换）

`FileMesh.chooseMode()` 在接收端点「接收」时读取 `room.members.size`：`<=2` 用 **direct**，`>=3` 用 **mesh**。
模式一旦确定，本次传输保持不变（第三人中途加入不会打断正在进行的快传，新发起的传输才走 P2P）。
续传时沿用进度记录里的 `mode` 与 `block`，避免换设备后帧大小不一致。

#### 8.2.1 direct：两人连续字节流（无分片、无位图、无多源）

```
1. 接收端广播 have_req 收集供种者 → 单播一次 direct_want{fid,gen,offset,block}
2. 源端从 file.slice(offset) 起按 4MB 段循环；发送当前段时并行预读下一段
3. 段内按协商 block（最大 1MB）切帧，批量加密（仅私有房）后连续 pushDirect
4. bufferedAmount 达 2MB（直传水位）→ waitDrain（drain 事件 / 16ms 兜底）→ 继续
5. 接收端按帧头绝对 offset 把字节追加到当前段缓冲；无序通道提前到达的
   后续段帧暂存 future，段推进后再应用
6. 段收齐 → putSegment 一次事务落 4MB Blob → offset += 段长 → 立即写进度
7. offset === size → direct_stop / file_stop → assembleDirect → 保存 → file_done
```

应用层没有分片索引、位图、取模分工、逐片请求、进度广播、重分工和重复片循环；
物理上仍受 SCTP 单消息上限约束而分帧，但接收端只做「按 offset 追加」，
**断点续传只需要一个段对齐的 `offset` 整数**。断线最多回退一个 4MB 段。

#### 8.2.2 mesh：三人及以上的多源 P2P 分片

```
1. 接收端广播 have_req 收集位图 → 按在线源数取模分工（最多 4 源）
2. 每个源单播一次 file_want{fid,gen,want,mod,total}（want = 缺失位图）
3. 源启动 pump：按 cursor 扫描，只推 i % total === mod 且 want[i]=1 且本端持有的片
4. 每批 32 片：双缓冲预读（File 并发 slice / 供种者一次 IDB 范围读 getChunks）
   → 并发加密（仅私有房）→ 连续 pushData 发送
5. bufferedAmount 达 8MB → waitDrain → 继续
6. 接收端重复片丢弃 → 置位 + 批量写 IDB（32 片/事务）
7. 每 8MB 广播 file_have；每 3s 发 file_got 让源跳过已收片
8. 1s 监控统计实时/峰值速率；停滞 8s 才排除停摆源并重新分工
9. havePieces === count → file_stop → flush 写队列 → assemble → file_done
```

#### 8.2.3 调优要点

- **水位 768KB → 分片 8MB/4MB、直传 2MB/1MB、WS 中继 4MB/1MB**：三组独立常量，按各自链路的在途量设定。原 768KB 窗口过小，网络抖动时反复等待，把连续推流切成脉冲，是「峰值 9.5MB/s、当前 0.77MB/s」的主要成因之一。
- **`STALL_MS 4s → 8s`、`file_got 5s → 3s`**：原停滞阈值比位图同步周期还短，
  每次重分工都会重发刚收到的片，形成「越慢越重发」的自激。
- **双缓冲预读**：发送当前批/段时并行读下一批，读盘与 IDB 不再打断连续 `send()`。
- **`direct` 通道 `ordered:false` 但保持可靠**：避免单个丢包队头阻塞，由接收端按 offset 重组。
- 公开房跳过应用层 AES-GCM（`mesh.setKey(null)`），WebRTC **DTLS 仍保护链路**；私有房保持端到端加密。
- 供种端 `getChunks()` 一次事务读一批，接收端 `putChunks()` 一次事务写 32 片；未落盘分片通过 `writeQueue`/`writing` 仍可供种。

**兼容性**：协议与旧版本不兼容（已确认可接受）。旧端发来的 `file_req` 仍会回单片避免完全卡死。

### 8.2.4 断点续传与抗息屏

- **进度落盘**：正常传输每 1s 节流写一次；每个直传段边界立即写；`pause` / `finish` / `cancel` / WS `close` 立即写。mesh 写进度前先 `flushWrites()`，保证位图不超前于已落盘数据。
- **恢复**：`registerOffer()` 异步 `hydrate()`，按 `fid` 与 `meta.size/count` 校验后恢复 `bits` 或 `offset`；断线前为 `running` 的传输自动恢复为 `running` 并重发 `have_req` / `direct_want`，无需再点「接收」。
- **自动重进房**：房间号与密码只存在 `sessionStorage`（`lanshare.resume`，关标签页即失效）。WS 重连后的 `welcome` 不再提示「请重新加入房间」，而是自动 `enter`；`enter` 语义本身就是「存在则加入、不存在则按该号新建」。`teardown()` 串成落盘链，保证新会话读到的是旧会话写完的进度。
- **Wake Lock**：传输期间请求 `navigator.wakeLock.request('screen')` 阻止自动息屏（需 HTTPS/localhost）；页面隐藏时系统自动释放，回到前台重新申请并 `rebalanceAll()` 重建推流。不支持时退化为「息屏断线 → 回来续传」，底部提示相应文案。
- `visibilitychange` / `pagehide` / `freeze` 立即 `persistAll()`，把已收数据写入 IDB。
- **发送端限制**：用户选中的 `File` 对象无法跨页面恢复，因此**分享方**页面被系统重载后仍需重新选文件；但接收方已收的字节不会丢。

### 8.3 交互规则

- 文件先只广播 `file_offer` 卡片；**用户点「接收」才订阅推送**，否则不产生任何文件流量（第 8 条）。
- 历史同步的卡片也会补建 leecher；点「接收」时向**全房**广播 `have_req`，因此发送者不是房主时同样能应答。收到有效 `file_have` 位图即解除卡片的过期标记；在线成员离开时清理其位图，避免幽灵源。
- 卡片渲染时即带「接收」按钮（不等待 transfer 就绪）；点击时若 `transfers` 仍无该 fid，从 `room.history` 兜底补建。空闲状态显示真实可用源数，便于判断后加入成员能否下载。
- 卡片显示：名称、大小、发送者、可用源数、进度条、接收/暂停/取消按钮。
- 「清理缓存」删除 IDB 分片后把状态机复位回 `idle`（清 `blob`/`bits`/`assign`/`stats`/`peerBits` 等）并广播 `file_stop`，卡片重新出现「接收」按钮，可再次下载。
- 卡片在下载中显示**传输模式（直连 / P2P）、实时速率、峰值速率、源数、去重数、异常数与已续传量**；「等待在线源」表示当前无可用供种设备。峰值可与同网 HTTP 下载对比，用于判断链路上限。
- 有保存进度时卡片显示「已保存进度 …，点接收继续」；暂停态标注「可断点续传」。已完成但页面重载过的文件可点「再次保存」从 IDB 重新组装，不必重新下载。
- 底部在传输期间显示「屏幕保持常亮」（Wake Lock 可用）或「息屏可从断点续传」（不可用）。
- 移动端 `navigator.connection.type !== 'wifi'` 时默认不响应 `file_want`（不供种），UI 提供「允许流量供种」开关。
- 单文件 >2GB 直接拒绝并提示（桌面与手机一致）。

## 9. 部署（默认单进程单端口 / 可选 coturn / Nginx 反代）

### 9.1 组件与端口

| 组件 | 端口 | 默认 | 说明 |
|---|---|---|---|
| Nginx | 443 tcp | 启用 | 对外 HTTPS/WSS，持有正式证书 |
| `lanshare` | 8080 tcp | 启用 | 页面 + WS 信令 + WS 中继；compose 映射 `"8080:8080"`（监听所有网卡，生产建议限制回环） |
| WS 完整中继 | 复用 443 tcp | 启用 | 默认模式，无新增端口 |
| STUN | 19302 udp 或自建 3478 | 不启用 | 只有配置了 `LANSHARE_STUN_URLS` 才使用 |
| `coturn` | 3478 udp+tcp | 不启用 | 仅 `--profile turn` 时启动：STUN 打洞 + TURN 信令 |
| `coturn` 中继 | 裸机 49152–65535 udp / Docker 40000–40200 udp | 不启用 | 仅 `--profile turn` 时的 TURN 中继端口段 |

默认部署只有 `lanshare` 一个进程/容器，防火墙只需放行 `443 tcp`。`coturn` 是可选 profile，启用时两者共享同一个 `TURN_SECRET`；`lanshare` 不需要主动连接 coturn，只负责签发临时凭据。`HTTP_PORT` 目前只用于说明 Nginx 的反代目标，compose 端口仍硬编码为 `8080:8080`。

### 9.2 推荐生产形态

```
浏览器 ──HTTPS/WSS──> Nginx(证书) ──HTTP/WS──> lanshare :8080
   │                                              │
   │                    默认模式：同一条 WSS 连接承载聊天 + 文件的服务器中继
   │
   ├── WebRTC DataChannel(P2P) ────────────────> 其它浏览器（内网直连 / 配了 STUN 时打洞）
   └── STUN/TURN(UDP) ───────> coturn :3478（可选，仅 --profile turn 时存在）
```

TLS 在 Nginx 终止，后端用 `-no-tls`（`LANSHARE_NO_TLS=1`）。浏览器仍是安全上下文，`wss://` 由 Nginx 降级代理到后端 `ws://`，WebRTC 不受影响。默认模式不需要图中最后一条 UDP 链路。

### 9.3 Docker Compose（默认无 coturn，Q3）

`docker-compose.yml` 只需配合 `.env` 即可部署：`lanshare` 使用已发布镜像，`coturn` 放在 `profiles: ["turn"]` 下按需启用。默认 `.env` 里 `STUN_URLS` / `TURN_URLS` 都留空，服务端下发 `noIceServers=true`，跨网直接由服务器 WS 完整中继，因此无需 UDP 端口、无需 TURN 密钥、也无需任何外部打洞服务器。

```bash
cp .env.example .env
# .env 开箱即用（HTTP_PORT 默认 8080）；PUBLIC_HOST 仅启用 --profile turn 时需要
docker compose up -d                                # 不拉取源码、不 --build
docker compose --env-file .env.example config --quiet

# 可选：启用标准 TURN
openssl rand -hex 24                                # 写入 TURN_SECRET
# .env 中再填 STUN_URLS、TURN_URLS、TURN_EXTERNAL_IP（NAT 后公网IP/内网IP）
docker compose --profile turn up -d
```

#### 9.3.1 两种部署模式与中继带宽（集中速查）

| 项 | 默认：无外部 ICE | 配置了 STUN / TURN |
|---|---|---|
| 触发条件 | `ICEConfig()` 下发的 `iceServers` 为空 → `noIceServers=true`（两个变量都留空，或配了 `TURN_URLS` 却缺 `TURN_SECRET`） | `iceServers` 非空 |
| 局域网 | 仍优先 `host` candidate 直连，给 2.5s 窗口 | 同左，由 ICE 自行协商 |
| 跨网 | 直接由服务器经 WS 完整中继聊天 + 文件 | `host` → `srflx` 打洞 → `relay` TURN；全员 ICE 明确失败才落 WS 兜底 |
| 额外端口 | 无（复用 443） | 配 STUN 需 UDP 出站；启用 coturn 需放行 `3478 udp+tcp` 与 `40000-40200 udp` |
| 外部依赖 | 无 | 公共 STUN 或自建 coturn |
| 速率 | 服务端**默认不限速**，背压只做流控 | 同左（WS 兜底时） |

中继带宽三处变量一一对应：`-relay-rate`（flag）↔ `LANSHARE_RELAY_RATE_MB`（进程环境变量）↔ `RELAY_RATE_MB`（compose 的 `.env`）。单位 MB/s、按单个 WS 连接计，`0` = 不限速；设置后使用 `rate / burst=2×rate` 令牌桶。帧数（1000 帧/s、突发 2000）与单帧大小（base64 文本 ≤256KB）始终是硬限制。详见 6.4 限流表、7.2 网格与 10 已知限制。

设计取舍：

- **不拉项目即可部署**：coturn 入口脚本已内联到 compose 的 `entrypoint`（compose 里 `$$` 转义为容器内 shell 的 `$`），不再挂载 `deploy/coturn-entrypoint.sh`；运行只需 `docker-compose.yml` + `.env`。`deploy/turnserver.conf`（含占位符）只用于裸机 coturn，Docker 版不读它。
- **两个变量共同决定模式**：`LANSHARE_STUN_URLS` 与 `LANSHARE_TURN_URLS` 都为空时 `ICEConfig()` 下发 `noIceServers=true`，前端直接走 WS 中继；任一非空则按配置走 ICE。准确条件是「最终下发的 `iceServers` 为空」，详见 9.3.1。`.env` 用 `STUN_URLS` / `TURN_URLS` 显式控制，默认都留空。若 `STUN_URLS` 指向 coturn 的 `3478`，停用 coturn 时要改掉或留空，否则浏览器会一直等一个不存在的打洞服务器。
- **中继不新增端口**：`relay` / `relay_data` 都走已有 443 的 WebSocket，Nginx 只需支持 Upgrade；`client_max_body_size` 只作用于 HTTP body，不影响升级后的 WS 帧。
- **中继带宽默认不限速**：compose 注入 `LANSHARE_RELAY_RATE_MB: "${RELAY_RATE_MB:-0}"`，`.env` 默认 `RELAY_RATE_MB=0`；只有显式填了 MB/s 才创建字节配额限流器。前端 WS 背压水位同步放宽到 4MB / 1MB，避免高速链路被切成脉冲。
- **中继端口收窄为 40000–40200**（仅可选 coturn）：避免 Docker 为 16384 个端口生成上万条 iptables 规则；10 人房间足够。Linux 上可改用 `network_mode: host` 并删掉 `ports`，但需启用 Docker host networking。
- **`LANSHARE_TRUST_PROXY=1` 必开**：否则所有用户出口 IP 都是 `127.0.0.1`，跨城市用户会被误判成同一局域网并互相看到房间。服务在非回环地址以 HTTP 启动且未开此项时会打印警告。
- 后端端口目前硬编码为 `"8080:8080"`（监听所有网卡），`HTTP_PORT` 未被 compose 使用。生产环境应改成 `"127.0.0.1:8080:8080"` 或用防火墙限制：后端开启了 `-trust-proxy`，外部绕过 Nginx 直连 8080 可伪造 XFF。

### 9.4 Nginx 反代要点

`deploy/nginx.conf.example` 给出完整示例，三个必配项：

1. `proxy_set_header Host $host;` —— WS 升级校验 `Origin`，Host 与浏览器域名不一致会返回 `origin not allowed`。服务端同时支持 `X-Forwarded-Host` 兜底。
2. `proxy_set_header X-Forwarded-For $remote_addr;` —— **覆盖**而非追加 `$proxy_add_x_forwarded_for`，防止客户端伪造 XFF 骗取同网分组。
3. `proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection $connection_upgrade;` —— `/ws` 才能升级；`proxy_read_timeout` 需大于 WS 的 25s ping 间隔。

### 9.5 HTTPS 四种方式

1. **公网 Nginx 反代（生产推荐）**：证书由 Nginx 提供，后端 `-no-tls -trust-proxy`，手机零配置。
2. **程序直接持证书**：`-addr :443 -cert fullchain.pem -key privkey.pem`。
3. **局域网自签**：`-export-cert deploy/cert/lanshare`，日志给出 `localhost` 与私网 IP 地址；安装并信任 `.crt`（iOS 需装描述文件并开启完全信任），之后用 `-cert/-key` 固定复用。
4. **开发**：`-addr :8080 -no-tls`，仅 `http://localhost:8080` 可用（手机不能这样访问）。

自签模式下，浏览器未信任证书会发送 `remote error: tls: unknown certificate` 并断开握手，属于**客户端主动拒绝**而非服务端故障；此类预期噪音由 `tlsErrorFilter` 静默，安装证书后自然消失。同理 `scope=approx|::1|?` 只是经 IPv6 localhost 访问时出口 IP 未知，属正常推测分组。

## 10. 已知限制（验收时不要误判为 Bug）

1. 「同 LAN 自动发现」是**推测**：CGNAT / 同一出口 IP 的不同楼层 / 多级 NAT 会串房间；绑定网络标识可消除。
2. 浏览器拿不到 SSID、网关 MAC、子网掩码，也无法 UDP 广播，因此无法做到 100% 精确的 LAN 判定。
3. 对称 NAT + 无 TURN 时走服务器 WS 完整中继，聊天与文件都可用；服务端默认不限速，但上下行都吃服务器带宽，速度取决于实际链路，通常慢于 P2P；且中继复用 443，不额外占用 UDP 端口。需要限速时用 `LANSHARE_RELAY_RATE_MB`。接收端拥塞时会短暂降速并重传缺片。
4. 最后一个持有历史的人离线 → 历史消失；历史文件卡片可重新点「接收」，但仅当在线设备仍持有该文件本体时才取得到数据（Q5）。发送者刷新页面后浏览器持有的原始 `File` 对象不可恢复，需重新选择文件发布；**接收方已收数据存于 IndexedDB，不会因刷新丢失**。
5. `RTCDataChannel` 受 SCTP 拥塞控制与设备省电策略影响，可接近但无法保证打满物理带宽。1200M/2400M 是 PHY 协商速率，两台无线终端经同一 AP 互传还要占两次空口；单条有序可靠 SCTP 流的实测峰值约 9.5MB/s 属协议量级，不是链路故障。
6. iOS Safari / 移动端对后台标签页会限流或挂起 WebRTC。Wake Lock 仅在支持的浏览器 + 安全上下文下能阻止息屏；系统仍可能杀后台，此时靠进度落盘 + 自动重进房续传。
7. 房间号与密码为恢复会话暂存在 `sessionStorage`，只在当前标签页有效；主动「离开」或被踢/房间解散会清除。
8. 房间号进程重启即失效；无多实例/集群支持（若要多实例需引入共享状态，超出当前范围）。
9. 反代部署若未开 `-trust-proxy`、或 Nginx 未正确传 `Host` / `X-Forwarded-For`，会出现「所有用户被判为同一局域网」或 `/ws` 升级被拒；属配置问题，按 9.4 逐项检查。
10. 极端降级（P2P 打洞失败、改走 WS 中继）时，`key_req` / `key_sync` 这两个明文握手帧会经过服务端内存（不落盘）；正常 P2P 链路下服务端只见 AES-GCM 密文。文件分片与直传帧即使在中继时也是 AES-GCM 密文，服务端只透传 base64。
11. 默认不下发任何外部 STUN/TURN，跨网只能走服务器 WS 中继（速度取决于服务器带宽，默认不限速）；需要打洞必须显式配置 `LANSHARE_STUN_URLS`。若它指向 coturn 的 `3478`，停用 coturn 时要改掉或留空。
